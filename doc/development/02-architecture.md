# 02. 总体架构

## 架构目标

豆屿 Doyu 第一版架构服务于五条主链路：

1. 社区内容发布、浏览、互动和审核。
2. 图片上传、AI 拼豆图生成和图纸资产沉淀。
3. 自营商城下单、支付、发货和售后。
4. 玩家二手/定制直连、私信、评价和风控。
5. 用户签到、等级、消息和个人资产。

## 系统分层

```text
Android App
  -> API 服务 /api/v1
    -> 用户与认证模块
    -> 社区内容模块
    -> AI 图纸任务模块
    -> 商城订单模块
    -> 支付模块
    -> 消息模块
    -> 审核与风控模块
    -> 管理后台模块
  -> PostgreSQL
  -> Redis
  -> 消息队列
  -> 对象存储 OSS
  -> 内容审核服务
  -> AI Provider
  -> 微信支付 / 支付宝
```

## 核心数据流

### 用户登录

1. 客户端提交手机号验证码或第三方授权凭据。
2. 后端校验身份。
3. 后端返回 access token、refresh token 和用户摘要。
4. 客户端安全保存 token。
5. 后续请求携带 `Authorization: Bearer <access_token>`。

### 社区发帖

1. 客户端申请上传凭证。
2. 客户端直传图片或视频到对象存储。
3. 客户端提交帖子文本、媒体 Key、话题和关联图纸。
4. 后端创建帖子，状态为审核中或可见。
5. 审核服务处理文本和媒体。
6. 审核通过后进入 Feed。

### AI 拼豆图生成

1. 客户端上传输入图。
2. 客户端创建 AI 任务。
3. 后端记录任务并进入队列。
4. AI 编排服务做输入审核、预处理、模型调用、拼豆算法、输出审核。
5. 结果文件保存到对象存储。
6. 后端更新任务状态。
7. 客户端轮询或接收通知后展示图纸。

### 自营商品支付

1. 客户端提交购物车和收货信息。
2. 后端校验价格、库存、优惠和地址。
3. 后端创建订单和支付单。
4. 客户端拉起微信或支付宝。
5. 支付渠道回调后端。
6. 后端验签、幂等处理、更新订单。
7. 客户端查询最终订单状态。

### 玩家直连交易

1. 卖家通过实名校验后发布二手或定制内容。
2. 买家浏览玩家市场或从作品页进入卖家主页。
3. 买卖双方通过私信沟通。
4. 平台记录交易线索、订单意向、举报和评价。
5. 高风险内容、外部联系方式、诈骗话术进入风控。

## 部署边界

第一版建议部署为：

- 一个 Android 客户端。
- 一个后端 API 应用。
- 一个后台管理 Web 应用。
- 一个 PostgreSQL 实例。
- 一个 Redis 实例。
- 一个对象存储 Bucket。
- 一个队列服务。
- 一个内容审核服务接入。
- 一个或多个 AI Provider 接入。

后续在 AI 任务量、支付订单量或社区流量明显增长后，再考虑拆分独立服务。

## 可观测性

必须记录：

- `traceId`。
- 用户 ID。
- 请求路径。
- 接口耗时。
- 错误码。
- AI 任务 ID。
- 订单 ID。
- 支付单 ID。
- 上传文件 Key。
- 审核记录 ID。

必须监控：

- 登录成功率。
- 上传成功率。
- AI 任务成功率和耗时。
- 支付成功率。
- 支付回调失败数。
- Feed 接口耗时。
- 队列堆积。
- 内容审核延迟。
- 崩溃率。

## 失败兜底

- 客户端支付返回仅作提示，最终状态必须查询后端。
- AI 任务失败需要明确失败原因和次数返还策略。
- 上传失败可重试，重复提交必须去重。
- 审核中内容不可进入公开推荐。
- 支付回调重复必须幂等。
- 服务端不可依赖客户端传入金额、库存、用户等级、卖家实名状态。
